# 预案质量检查增强（一致性 / 合规性 / 可执行性）— 设计规格

> **日期**：2026-08-10 | **状态**：设计中 | **依赖**：预案生成增强、预案附图扩展（均已上线）

---

## 1. 概述

在现有 `plan_quality_service.check_plan` 的 6 条规则基础上，新增三组质量检查：

1. **一致性检查**——跨章节人物一致性、档案 vs 正文冲突、响应分级/术语数字混用。
2. **合规性检查**——章节结构是否符合 GB/T 29639-2020、法规引用真实性、术语统一。
3. **可执行性检查**——联系电话格式、关键岗位覆盖、应急资源充分性。

同时修正现有规则的粒度问题（地址/法人/安全负责人从「逐章节」改为「必含章节检查」、地址关键片段匹配），并明确 issue/warning 分级。

全部为**纯规则实现、零 LLM 调用**，在 `check_plan` 函数内扩展，不改变现有接口与调用方。

## 3. 规则设计

### 3.0 基础修正（贯穿）

**a. 检查粒度：逐章节 → 必含章节**

地址/法人/安全负责人「未体现」检查仅作用于必含章节：

| 预案类型 | 必含章节 |
|---------|---------|
| comprehensive | sec_2 事故风险描述 |
| special | sec_1 事故风险分析 |
| onsite | sec_1 事故风险提示 |

其余章节不再报「正文未体现企业档案××」。

**b. 地址匹配：整串 → 关键片段**

从档案地址提取关键片段（市级以上/区县/路街/门牌号级别的标记，如「民经一路726号」）与正文做归一化包含匹配；正文含任一片段即视为已体现，消除「陕西/2幢12402室」前缀缺失造成的误报。

**c. 分级**

- `issues`（阻断导出）：仅保留「必含章节缺失或内容为空」。
- `warnings`（提示不阻断）：其余全部规则（含新增三组）。

---

### 3.1 一致性检查

**规则 C1：跨章节人物一致性**

- 从全文提取「职务 → 姓名」映射：正则匹配 `总指挥（?:：|为|是)?\s*([\u4e00-\u9fa5]{2,4})`、`副总指挥...`、`安全负责人...`、`组长...` 等。
- 同一职务在不同章节出现不同姓名 → warning：`「{章节A}」写{职务}为{姓名A}，「{章节B}」写为{姓名B}，请核实`。
- 与档案 `org_structure` 比对：正文职务姓名与档案中该职务成员不一致 → warning：`正文{职务}为{姓名}，与企业组织架构不符`。

**规则 C2：档案冲突检测（升级现有「未体现」）**

- 正文出现的地址片段与档案关键片段**冲突**（如同为「市/区」但路名不同）→ warning：`疑似地址与档案不一致`。
- 正文出现的法定代表人/安全负责人姓名与档案不一致 → warning：`疑似法定代表人（安全负责人）与档案不一致`。
- 与 C0 的关系：C0 管「没写」，C2 管「写了但不对」。

**规则 C3：数字/术语混用**

- 响应分级混用：全文同时出现 `III级/II级/I级` 与 `一级/二级/三级` → warning：`响应分级表述不统一`。
- 时限单位混用：同时出现 `分钟` 与 `小时` 且数值**不等价**（如「30分钟」与「2小时」并存；「30分钟」与「0.5小时」等价不报）→ warning：`时限表述不统一`。

---

### 3.2 合规性检查

**规则 L1：章节结构合规**

- 按 `plan_type` 对照模板：`required=True` 的顶层章节若预案中不存在或内容为空 → issue：`缺少必含章节：{标题}`。
- 数据来源：模板结构（`seed_templates.py`）或预案章节实际存在性。

**规则 L2：法规引用真实性**

- 从正文提取引用：
  - 书名号：`《([^》]{2,60})》`
  - 标准号：`GB/T?\s*\d+[-—]\d{4}` 与 `GB\s*\d+[-—]\d{4}`
  - 令号：`（[^）]{0,20}?第?\s*\d{3,4}\s*号）`
- 与法规库 `graph.json` 的 `full_name`/标准号做归一化包含匹配（去空格、全半角归一）。
- 库中不存在 → warning：`疑似引用不存在的法规：《{引用}》`。
- 库中存在但标记已废止 → warning：`《{引用}》已废止，请核实`。
- 法规库不可用时静默跳过（不报错、不误报）。

> **暂缓说明（2026-08-11）**：L2 存在性判定因法规库数据质量（大量 article 节点、测试节点混入、法规名写法不统一）暂缓启用；仅保留引用提取函数 `_extract_regulation_refs`，待法规库数据治理后恢复存在性/废止判定。

**规则 L3：术语统一**

- 与 `prompt_cache.COMPLIANCE_BLOCK` 术语表对齐，检测混用：
  - `应急救援指挥部` vs `应急指挥部`
  - `应急救援小组` vs `应急小组`
  - 同一术语两种写法并存 → warning：`术语表述不统一：{A} 与 {B} 混用`。

---

### 3.3 可执行性检查

**规则 E1：联系电话格式**

- 正文提取电话号码模式，非 `1[3-9]\d{9}`（手机）或 `0\d{2,3}-?\d{7,8}`（座机）的疑似号码 → warning：`疑似联系电话格式错误：{号码}`。
- 组织架构成员 `phone` 为空 → warning：`企业组织架构中{姓名}（{职务}）无联系电话`。

> **收敛说明（2026-08-11）**：正文电话格式检查已移除——正文数字语义判断纯正则不可靠，易误报身份证/证件号码等；E1 仅保留「组织架构成员无联系电话」完整性检查。正文电话格式校验留待后续（如需可接入 LLM 校验）。

**规则 E2：关键岗位覆盖**

- 档案 `org_structure` 全成员中无「总指挥」或「副总指挥」职务 → warning：`企业组织架构缺少总指挥或副总指挥`。
- 正文「应急指挥机构」类章节有内容但档案无总指挥 → warning：`正文提及应急指挥机构，但企业组织架构未设置总指挥`。

**规则 E3：应急资源充分性**

- `EmergencyResource` 无「消防/灭火」类 → warning：`企业未登记消防/灭火类应急资源`。
- 无「急救/医疗」类 → warning：`企业未登记急救/医疗类应急资源`。
- 有风险点但应急资源数量均为 0 的类别 → warning：`{类别}应急资源数量为 0`。

## 4. 输出结构

保持 `check_plan` 返回结构不变：

```python
{
  "valid": bool,
  "issues": [{"section_key", "section_title", "issue"}],
  "warnings": [{"section_key", "section_title", "warning"}],
}
```

新增规则均返回 warning 或 issue 字典，`section_key`/`section_title` 为触发规则对应的章节（法规/组织/资源类全局规则用首个触发章节或空串）。

## 6. 测试计划

- C1：构造两章节同一职务不同姓名 → 断言 warning；与档案比对不一致 → warning。
- C2：正文地址片段与档案冲突 → warning；正文法人姓名与档案不符 → warning。
- C3：III级与一级混用 → warning；30分钟与2小时并存（不等价）→ warning；30分钟与0.5小时并存（等价）→ 不报。
- L1：缺必含章节 → issue；全部存在 → 无。
- L2：mock graph.json，存在/不存在/已废止三种引用断言；法规库不可用静默。
- L3：术语混用 → warning。
- E1：非标准电话格式 → warning；成员无 phone → warning。
- E2：无总指挥 → warning；有总指挥 → 无。
- E3：无消防类资源 → warning；资源全 0 → warning。
- C0：地址片段匹配不再误报；逐章节未体现改为仅必含章节。
- 回归：后端全量（容器 318+ 基线）、前端 tsc + vitest。
