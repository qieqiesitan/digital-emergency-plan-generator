## 1. 背景与目标

### 1.1 背景

产品主线从「数字化应急预案自动生成系统」转为「**安全生产管控平台（AI 能力深度融合）**」。预案生成不再是主线，而是平台内的一个模块（"预案与应急管理"），继续作为 AI 价值的展示窗口。

对标系统已详细探索（第三方商业产品，**无源码、无授权**），本设计**不复制其代码、界面、字段命名与文案**，业务规则一律依据国家标准与行业规范自研。

### 1.2 目标

1. 补齐安全生产管控的三个缺失域：**重大危险源、特殊作业（作业票）、数据接入**。
2. 把已有能力（风险分级管控、隐患排查治理）与新模块打通，形成「风险 → 重大危险源 → 隐患 → 作业票 → 预案」的完整证据链。
3. 让"AI 深度融合"从口号变成架构属性：**每条数据可溯源到法规条文，每次 AI 调用可追溯、可计量、可降级**。

### 1.3 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 教育培训 / 考试 | 通用件，与 AI 差异化无关 |
| 应急演练、监测报警、SIL 等级评估 | 依赖硬件或数据积累，后置 12 个月以外 |
| AI 视频分析、人员定位 | 依赖外部厂商与硬件生态 |
| 通用 BPMN 工作流引擎 | 见 §7.4 |
| 通用 ETL 框架 | 见 §8.1 |
| CA 电子签名 | 采"电子化流程 + 打印纸质签字"混合模式 |
| 复制对标系统的界面与文案 | 合规红线 |

### 2.2 真实缺口

1. **重大危险源台账 + R 值法分级** —— 业务代码中"重大危险源"仅 1 处（提示词文本），"临界量"0 命中

4. **AI 调用可观测** —— `token_usage|llm_call|ai_call_log|usage_log` 0 命中，无任何调用记录

### 2.3 重复建设红线

不重做风险分级管控与隐患排查治理；不新建"数据中台"式框架；不引入 Flowable/Camunda；不用 AI 算 R 值；不一次做 8 类作业票；不砍掉预案生成。

## 3. 总体架构

### 3.1 分层与增量

架构形态不变：仍是**单企业为主键的多企业单体应用**（FastAPI + PostgreSQL + React 18 + antd），不引入微服务、消息队列、BPMN 引擎。

```
现有（保持）                              本次新增
├─ FastAPI 单体 + PostgreSQL              ├─ 模块层：重大危险源、特殊作业（11 → 13 个模块槽位）
├─ React 18 + antd 5 前端                 ├─ 依据层：evidence_refs（数据 → 法规条文）
├─ 11 个企业模块（注册表驱动）             ├─ AI 网关：就地增强 services/llm_client.py
├─ 55 + 36 个风险/隐患端点                └─ 接入层：DataHub（来源注册/映射/同步/对账）
└─ 24 个既有 AI 端点 + 160+ 份法规库
```

### 3.2 目标模块树（企业维度 13 个）

```
基本信息 / 组织架构 / 周边环境 / 危险化学品 /
重大危险源★ / 风险分级管控 / 隐患排查治理 / 特殊作业★ /
应急资源 / 应急预案 / 风险评估报告 / 资源调查报告 / 字典配置

（★ = 本次新增）
```

## 4. 依据层（evidence_refs）

### 4.1 目标

平台级能力：**任何一条管控措施、隐患判定、危险源分级结论，都能挂到具体法规条文并点开看原文。** 这是对标系统做不到的，也是本平台的差异化根基。

### 4.2 数据模型

新表 `evidence_refs`（多态引用，不改动已有业务表结构）：

| 字段 | 说明 |
|---|---|
| `owner_type` | 归属实体类型（`risk_measure` / `hazard_record` / `major_hazard_unit` / `work_ticket_measure` …） |
| `owner_id` | 归属实体 id |
| `regulation_id` | 法规 id（复用 `regulations` 体系） |
| `article_anchor` | 条文锚点（如 `GB 30871-2022 5.3.2`） |
| `relation` | 关系类型：`依据` / `引用` / `冲突` |
| `note` | 引用理由 |
| `created_by` / `created_at` | 留痕 |

实现按 `(owner_type, owner_id)` 建索引；条文原文不冗余存储，实时按 `article_anchor` 取，避免法规修订后数据不一致。

### 4.3 接入范围与顺序

1. **P0**：重大危险源（GB 18218 第 4 章与表 3~表 6）
2. **P0**：作业票安全措施库（GB 30871 第 5~12 章）
3. **P1**：风险管控措施（`RiskMeasure`）
4. **P1**：隐患认定依据（`HazardRecord`）

### 4.4 前端交互

在措施/判定条目上提供「依据」入口，侧栏展示条文原文与出处；生成报告时可选"附法规依据"。

## 5. AI 调用网关（就地增强 `llm_client.py`）

### 5.1 现状问题

实测（含 `docs/系统诊断报告-2026-09-17.md`）：

- **B1 超时错误映射失效**：`llm_text_completion` 的 `except httpx.TimeoutException → 504` 是死代码（`_post_with_retry` 已把超时包成 `LLMError(0)`），用户看到 `500 + "AI调用失败: 0"`
- **B2 流式截断静默通过**：`_stream_response` 在供应商中途断开时正常 `return`，半截文本被当作完整结果落库
- **无调用留痕**：全库 `token_usage|llm_call|ai_call_log|usage_log` 0 命中
- **无按能力选模型**：只有单一系统级 `AIConfig`

### 5.2 设计

在 `llm_client.py` 内部增加（不新建旁路网关）：

1. **统一调用埋点**：每次调用记录 `module` / `capability` / `model` / `prompt_version` / 耗时 / token / 成功失败 / 重试次数 / 是否截断。落库新表 `llm_call_logs`；写入失败不得影响主流程（best-effort）。
2. **按能力选模型**：`AIConfig` 增加能力级覆盖（能力名 → 模型/参数），未配置回落到系统级配置。
3. **法规条文注入**：提供统一的上下文拼装入口，把 `evidence_refs` / 条文匹配结果注入提示词。
4. **结构化输出校验**：抽取类调用强制 JSON schema 校验，失败重试一次后转人工。
5. **修复 B1/B2**：B1 改为识别 `LLMError(status=0)` 并映射 504；B2 在断流时回传截断标记，由调用方决定重试或报错（章节生成必须报错，不得落库半截）。

### 5.3 错误处理与降级

| 情形 | 处理 |
|---|---|
| 429 / 5xx | 指数退避重试（沿用现 `RETRYABLE_STATUS`，默认 3 次） |
| 401 | 不重试，提示重新配置 API Key |
| 超时 | 重试后仍失败 → **504**（修复 B1） |
| 流中断 | 抛出可识别异常或回传截断标记 → 调用方决策（修复 B2） |
| 结构化校验失败 | 重试一次 → 转人工确认 |

### 5.4 成本与可观测

按 `module`、`capability`、`model` 维度出用量与失败率；为后续"AI 能力注册表 + 管理页"（P2）预留字段。

**业务表**

| 表 | 关键字段 |
|---|---|
| `major_hazard_units` | `enterprise_id`、`name`、`unit_type`(生产单元/储存单元)、边界描述、`floor_id` + 平面图多边形（复用现有机制）、责任部门/责任人/电话、`risk_object_id`（关联风险点，可空）、启用状态 |

| `major_hazard_calculations` | **只追加、不可变**：`unit_id`、`s_value`、`r_value`、`alpha`、`exposed_population`（厂外 500m 常住人口）、`inputs_snapshot`(JSONB：每品种 q/Q/β/q÷Q 与数据来源)、结论、等级、`formula_version`、计算人/时间 |
| `major_hazard_records` | 档案与备案：`unit_id`、`hazard_code`、备案状态/号/日期、**包保责任人**（主要负责人/技术负责人/操作负责人 × 姓名/职务/电话）、附件（安全评价报告、评估报告、平面图、包保公示牌）、资料完整性状态 |

### 6.2 R 值法计算（确定性，AI 不得参与）

依据 GB 18218-2018（已核实原文，`regulations/data/texts/reg_gb_18218_2018.md`）：

- **辨识**：单品种 `q ≥ Q` 即构成；多品种按式(1) `s = q1/Q1 + q2/Q2 + … + qn/Qn ≥ 1` 构成
- **分级**：式(2) `R = α × Σ βi × (qi/Qi)`
  - α 按表5（厂区边界外扩 500m 内可能暴露人员数）
  - β 优先按表3（14 种毒性气体名称），未命中按表4（危险性类别 J1~J5 / W1.1~W11）
- **级别**：按表6（一级 R≥100、二级 100>R≥50、三级 50>R≥10、四级 R<10）
- **实际存在量按设计最大量确定**（4.2.2）；混合物按 4.2.3 处理
- 公式常数写死在引擎内并带 `formula_version`；**单元测试对照标准算例回归**

每次计算落一条不可变快照（§6.1），保证可复算、可审计。

### 6.3 常量表种子数据

来源 `docs/标准数据-GB18218-2018/`（表1 85 条、表2 26 行、表3 14 条、表4 24 条、表5 5 条、表6 4 条），抽取脚本 `scripts/extract_gb18218_tables.py` 可复现。校验结论：序号连续无缺号、CAS 校验位 82 条全通过、无 CAS 3 条已视觉确认为原文即空。

### 6.4 AI 落点

1. 上传《安全评价报告》《重大危险源评估报告》→ 抽取单元、品种、设计最大量、厂外人口 → **带文件名/页码/置信度** → 进 DataHub 待确认队列 → 人工确认后入库
2. 生成辨识报告与备案材料初稿（复用 `report_docx.py` 公文版式）
3. 档案完整性检查：列出缺失资料
4. 从危化品台账建议单元划分（生产单元/储存单元边界）

### 6.5 与既有模块的关联

危化品台账 → 单元品种；`RiskObject` ↔ 单元；`EnterpriseFloor` 多边形 → 单元在四色图上的落点；`HazardRecord` 可关联单元；`PlanProject` 引用重大危险源清单；`evidence_refs` → GB 18218 条文。

### 6.6 报告与备案

输出「重大危险源辨识报告」；包保公示牌在线版后置（先出 DOCX）。

## 7. 作业票模块（特殊作业）+ 轻量审批引擎

### 7.1 范围

8 类：动火、受限空间、盲板抽堵、高处、吊装、临时用电、动土、断路。依据 GB 30871-2022（库内真原文 `regulations/data/texts/reg_gb_30871_2022.md`，63KB / 1136 行）。

**库内资产（已验证）**：

- **附录A = 表 A.1~A.8，8 类作业票的法定票面样式**，含逐条安全措施清单（带"是否涉及 / 确认人"列）
- **附录B 表 B.1 = 法定"办理部门 / 审核会签 / 审批部门"矩阵**（特级动火→主管领导；一级动火→安全管理部门；二级动火→所在基层单位；Ⅰ级高处/受限空间/盲板抽堵→所在基层单位；Ⅱ、Ⅲ级高处/二三级吊装/动土/断路→所在单位专业部门；Ⅳ级高处/一级吊装→主管厂长或总工程师；临时用电→配送电单位；动土→多单位会签）
- **表 B.2** 三联（持有/存档）规则；**B.3** 作业票至少保存一年、作业过程影像至少留存一个月
- 条款数：第4章通用要求 18 条、第5章动火 32 条、第6章受限空间 10 条、第7章盲板抽堵 12 条、第8章高处 16 条、第9章吊装 16 条、第10章临时用电 8 条、第11章动土 11 条、第12章断路 5 条

### 7.2 前置任务：GB 30871 文本清洗（P2-0）

库内文本存在**系统性 OCR 讹字**，实测：**"式"出现 0 次、"怯"出现 30 次**（样式→样怯、方式→方怯、便携式/移动式/隔绝式同理）；**"Ⅱ"出现 0 次、"聂"出现 4 次**（Ⅱ级→聂级）；"您"6 次（疑似"低"误识）。

**不修就 seed 措施库，用户会在动火票上看到"动火方怯"。** 修复策略：一对一映射批量替换 + 用「"式"出现次数 > 0 且 "怯" = 0」作为修复完整性判据 + 人工抽检。

### 7.3 数据模型

**模板层（8 类共用）**

| 表 | 关键字段 |
|---|---|
| `work_ticket_templates` | 作业类型编码（DHZY/YXKJ/MBCD/GCZY/QZDZ/LSYD/PTZY/DLZY）、名称、是否分级、法条锚点、启用状态 |
| `work_ticket_template_fields` | `key`、`label`、类型、必填、分组（基本信息/作业内容/危害因素/安全措施/气体检测/人员/签字）、序号、校验规则、是否允许 AI 预填 |
| `work_ticket_template_measures` | 该类型+等级的必备安全措施，逐条来自标准第 5~12 章，每条挂 `article_anchor` |
| `work_ticket_flow_templates` | 流程模板（绑定 `template_id`、企业可改） |
| `work_ticket_flow_nodes` | `node_key`、名称、序号、审批角色、**会签策略**（`all`/`any`）、进入条件、退回策略、超时 |

**实例层**

| 表 | 关键字段 |
|---|---|
| `work_ticket_instances` | 编号、模板、**`level`（作业等级，如动火的特级/一级/二级、高处的 Ⅰ~Ⅳ 级——审批条件分支依据此字段）**、状态、有效期起止、延期次数、作废原因、关联的其他作业票编号 |
| `work_ticket_values` | 字段值 + 填写人/时间 |
| `work_ticket_gas_tests` | 时间、点位、O₂/LEL/CO/H₂S 等、检测人、结论（动火票需多次取样，独立成表） |
| `work_ticket_persons` | 作业人/监护人、特种作业证号与**有效期校验** |
| `work_ticket_node_records` | 节点办理记录（谁、何时、同意/退回、意见、签名图） |

**留痕层**

`work_ticket_audit_log`（对齐 `HazardAuditLog`）、`work_ticket_print_snapshots`（内容 hash + 打印人 + 时间，打印后不可改，只能新建版本）。

**编号规则**：`{类型}-{企业码}-{YYYYMMDD}-{4位序号}`；序号按「企业+类型+日期」维度生成，**用数据库唯一约束防并发重号**，不依赖应用层判断。

### 7.4 轻量审批引擎（不引入 BPMN）

**理由**：Flowable/Camunda 是 Java 服务，与 Python 栈不匹配、运维翻倍、AI 难以介入解释；而 8 类作业票的流程本质是"固定模板 + 少量条件分支"，且**标准表 B.1 已给定审批人**，无需通用 BPMN。沿用 `hazard_state_machine.py` 的 `TRANSITIONS` + `ROLE_GATE` 范式，保持一致性。

三个概念：

- **流程模板** = 有序节点列表
- **节点** = 审批角色 + 会签策略（`all` 全部通过 / `any` 一人通过）+ 进入条件 + 退回策略
- **实例** = 流程模板 + 当前节点 + 办理记录

**条件分支用受限表达式**：只支持字段比较（如 `level in [1,2] && is_cross_dept == true`），不引入通用表达式引擎（安全 + 可解释）。

### 7.5 状态机与角色门控

```
draft(填写中) → submitted(待审批) → approving(审批中)
   ├─ rejected(已退回) → 回到 draft
   ├─ cancelled(已作废)
   └─ approved(已批准) → working(作业中) → finished(已完工) → closed(已归档)
approved 超期未开工 → expired(已过期)
```

角色**取自现有 `Role` 体系**（`roles`/`permissions`/`role_permissions`），不新建平行角色系统。节点绑定角色 code，角色成员可配置。

### 7.6 有效期与延期

批准后有效（默认按类型可配，如当日 / 8 小时）；延期走独立节点并留痕；到期由 APScheduler 自动置 `expired`（复用 `hazard_scheduler.py` 的调度范式）。

### 7.7 打印与归档

按附录 A 的法定格式生成 docx/html，复用 `services/docx_template.py`（已有表格、封面、签字页、页眉页脚能力）。打印时生成内容快照并落 hash，**之后任何修改只能新建版本**——审计追溯的底线。

### 7.8 AI 落点

1. **提交前合规校验**：必填项完整性、措施与作业类型/等级匹配（逐条对照 GB 30871 对应章节）、监护人特种作业证有效期、气体检测是否覆盖开工前 30 分钟内 → 问题清单。

   阻断或预警由**企业级开关**控制：在 `Enterprise` 上增加 `work_ticket_ai_check_mode`，取值 `off`（只提示） / `warn`（可继续提交） / `block`（禁止提交），默认 `warn`。**涉及法定必填项与证件有效期时，无论开关取值一律阻断**。
2. **JSA 生成**：作业内容 + 环境 + 设备 → 危害识别 + 预防措施
3. **审批辅助**：本条与历史同类票的差异点、每条措施对应条文原文
4. **历史相似票检索**：同装置、同类型作业的历史措施与案例

原则：**AI 只做提取、生成、建议、解释；审批、签字、有效期、留痕全部确定性代码。**

## 8. 数据接入适配层（DataHub）

### 8.1 定位与边界

**不是通用 ETL 框架，而是一条统一的数据落地通道。** 只支持三种形态：

| 形态 | 场景 | 触发 |
|---|---|---|
| 文件抽取 | 上传安全评价报告 / 重大危险源评估报告 → AI 抽取 | 人工上传 |
| 表格导入 | 危化品台账、风险点清单 Excel | 人工上传 |
| 系统对接 | 外部系统 REST 推送（HMAC）或我方定时拉取 | 推送 / 定时 |

三种形态最终都变成 `ingest_items` 的一条待确认项，**确认后才写入正式表**。这就是"总线"的本质。

**明确不做**：通用 ETL（无自定义算子、无复杂转换管道）；双向同步（只做单向入站）；实时流（不上消息队列）。

### 8.2 数据模型

| 表 | 关键字段 |
|---|---|
| `ingest_sources` | 类型（file/sheet/api_push/api_pull/manual）、名称、配置 JSONB、密钥引用（走 `third_party_config`，不落明文）、启用状态、默认目标实体 |
| `field_mappings` | 源字段 → 目标字段、转换规则（单位换算/枚举字典/日期格式）、是否必填、审核状态。**同一映射可复用** |
| `ingest_jobs` | 来源、触发方式、状态、统计（总数/成功/跳过/失败/待确认）、起止时间、错误摘要 |
| `ingest_items` | `job_id`、幂等键、`raw_payload`(JSONB)、目标表、目标 id、状态（pending/imported/skipped/failed/needs_review）、**来源定位**（文件+页码/段落）、**置信度**、确认人/时间 |
| `ingest_reconciliations` | 期望 vs 实际条数、校验和、差异说明、对账时间 |

### 8.3 四条硬规则

1. **原始载荷永久保留**：`raw_payload` 不删，任何时候可回答"这条数据当初长什么样、来自哪个文件第几页"
2. **落正式表前必须人工确认**：AI 抽取与外部推送一律先进 `ingest_items`（`pending`）；**无确认动作不进正式表**。不为"自动化率好看"而放宽
3. **幂等键强约束**：`(source_id, external_id)` 或内容 hash 唯一，重复推送不产生重复记录
4. **失败可重放**：失败项保留原始载荷，修完映射即可重跑，无需重新上传

### 8.4 AI 落点

1. **字段映射建议（schema matching）**：上传 Excel 后 AI 建议列 → 字段映射，人工确认后存入 `field_mappings`
2. **非结构化抽取**：复用并泛化 `services/onboarding_service.py` 的 `extract_candidates`，从 onboarding 的 6 个模块扩展到重大危险源、作业票措施库等新模块
3. **数据质量校验**：数值区间、单位异常、日期越界，以及 **CAS 号校验位验证**（算法已在 `scripts/extract_gb18218_tables.py` 实现，可直接复用）
4. **重复检测**：同企业相似记录聚类提示

## 9. 关键数据流

**流程一：资料 → 重大危险源台账**
上传 PDF → `file_parser` 转文本 → AI 抽取候选（带来源页码与置信度）→ `ingest_items`(pending) → 人工确认 → `major_hazard_units` / `_chemicals` → 触发计算 → `major_hazard_calculations`（不可变快照）→ 挂 `evidence_refs` → 生成辨识报告

**流程二：作业票全生命周期**
选择模板 → 填写（AI 预填）→ **气体检测记录录入**（动火/受限空间类为提交前必填）→ AI 合规校验 → 提交 → 审批引擎按 `work_ticket_flow_nodes` 逐节点办理（会签/或签、条件分支、退回）→ 批准 → 作业 → 完工 → 归档 → 打印快照

**流程三：风险 → 隐患 → 预案**
风险点/管控措施（已有）→ 隐患发现与闭环（已有）→ 作业票违规可生成隐患 → 隐患与重大危险源数据作为预案编制输入 → 预案生成（已有）

## 12. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 把 8 类作业票当 8 个独立功能做 | 工作量 ×8 | 强制模板驱动 |
| 2 | 做成通用 ETL / 通用 BPMN | 无底洞 | §8.1、§7.4 先写死边界 |
| 3 | 审批角色与企业实际组织对不上 | 流程跑不通 | 流程模板企业可改（标准明确"参照执行"） |
| 4 | 签字法律效力期望失控 | 后期扯皮 | 需求阶段讲清：电子化流程 + 打印纸质签字，不做 CA |
| 5 | AI 抽取污染正式数据 | 追溯成本高 | §8.3 硬规则 2，无确认不入正式表 |
| 6 | 来源接口不稳定 | 集成中断 | `raw_payload` + 可重放 |
| 7 | 数据重复入库 | 数据质量 | 幂等键数据库级唯一约束 |
| 8 | 合规红线（无源码复刻） | 法律风险 | 只按国标自研；不复制界面/字段命名/文案 |
| 9 | 定位漂移（退化成普通台账平台） | 差异化丧失 | 所有新模块从第一天挂 `evidence_refs` |
