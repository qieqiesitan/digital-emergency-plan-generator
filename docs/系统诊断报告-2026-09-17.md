## 二、P0 高危问题（建议 24–72 小时内处理）

### P0-1 前端静态服务器存在路径穿越，可读取容器内任意文件【实测】

- **位置**：`frontend/server.py` → `ProxyHandler._serve_static()`（`os.path.join(DIST_DIR, path.lstrip("/"))`，未做 `normpath`/前缀校验）；该文件由 `frontend/Dockerfile.mobile` 打成 `shuzihuayuan` 镜像（宿主机 8082）
- **实测证据**：

```bash
curl --path-as-is -s -i "http://127.0.0.1:8082/../../etc/passwd"
# → HTTP/1.0 200 OK，返回 root:x:0:0:root:/root:/bin/bash ...
curl --path-as-is -s "http://127.0.0.1:8082/../../proc/self/environ"
# → 200，返回容器环境变量（PATH/HOSTNAME/BACKEND_URL...）
```

- **影响面**：可读容器内任意文件（`/proc/self/environ`、应用配置文件、模型目录、脚本源码）。当前实测容器环境变量不含高敏凭据，但代码与配置全可读，且任何后续挂载进来的密钥文件都会被同一条路径读走。
- **影响范围界定**：公司现行拓扑是"宿主 nginx 托管静态 + 反代 /api"，nginx 会规范化 `..`，因此**该漏洞不在公司 nginx 形态下直接暴露**；但根 `docker-compose.yml` 的 `shuzihuayuan`、本地/演示环境（8082 已监听 0.0.0.0）以及 README 中"自托管前端"形态都会裸奔。
- **修复建议**：用 `os.path.realpath` 解析后校验必须以 `DIST_DIR + os.sep` 开头，否则 404；或直接删除自写 handler，改用 `SimpleHTTPRequestHandler.translate_path`（自带规范化）+ `directory=` 限制。修复后回归用例：`../`、`..%2f`、`//..//`、绝对路径、符号链接。
- **验证方式**：复跑上面两条 curl，必须返回 404。

### P0-2 导出文件下载接口无鉴权，可下载完整预案【实测】

- **位置**：`backend/app/routers/export_tasks.py::download_export`（`GET /api/v1/export/download/{file_key}`），无任何 `Depends(get_current_user)`，仅做 `^[\w\-.]+$` 文件名校验
- **实测证据**：

```bash
curl -o /dev/null -w "%{http_code} %{size_download}\n" \
  "http://127.0.0.1:8000/api/v1/export/download/西安宝岳空间科技有限公司-综合应急预案.docx"
# → 200 446307
```

- **文件命名可枚举**：导出文件名为 `{预案标题}.docx` / `{企业名}_事故风险评估报告.docx`（`export.py:399`、`risk_assessment.py:532`、`resource_investigation.py:271`），企业名+预案类型是公开信息，远低于 UUID 的猜测成本。
- **影响**：完整预案含企业组织架构、应急联系电话、风险清单、周边环境等敏感内容，属实际数据泄露。
- **修复建议**：① 该路由加 `Depends(get_current_user)`，并按 `plan/user` 归属校验再放行；② 同步给 `GET /api/v1/export/tasks/{task_id}` 加鉴权（当前也无鉴权）；③ 长期方案是改为"导出记录表 + 随机 file_key + 归属校验"。
- **验证方式**：无 token 请求应 401；用其他用户 token 请求他人预案应 403/404。

### P0-3 停止生成接口无鉴权【实测】

- **位置**：`backend/app/routers/generation.py:930`

```python
@router.post("/{plan_id}/generate/stop")
async def stop_generation(plan_id: str):
    _active_generations[plan_id] = False
    return {"code": 0, "message": "已请求停止生成"}
```

- **实测证据**：`POST /api/v1/plans/00000000-.../generate/stop`（无 token）→ `200 {"code":0,"message":"已请求停止生成"}`
- **影响**：任意匿名调用者可中断任意预案的生成（拒绝服务 + 浪费已消耗的 AI 费用）；虽然需要知道 plan_id，但 plan_id 会出现在分享链接/日志/前端历史中。
- **附带缺陷**：停止标记是进程内变量，4 worker 部署下**停止请求只有 1/4 概率命中真正在跑生成的那个 worker**，即"停止"本身不可靠。
- **修复建议**：加 `get_current_user` + 预案归属校验；把生成控制信号改为 DB/Redis 共享状态（见 P0-5）。

### P0-4 法规模块写操作的管理员校验被显式移除【代码实证】

- **位置**：`backend/app/routers/regulations.py`，以下 6 处均带注释 `# ponytail: admin check removed for usability`：

| 行号 | 端点 | 危险等级 |
|---|---|---|
| 295 | `POST /regulations`（新建法规） | 高 |
| 351 | `PUT /regulations/{id}`（修改法规） | 高 |
| 386 | `DELETE /regulations/{id}`（删除法规） | 高 |
| 419 | `POST /regulations/batch/abolish`（批量作废） | 高 |
| 458 | `POST /regulations/{id}/abolish`（作废） | 高 |
| 487 | `POST /regulations/rebuild-index`（重建向量索引） | 高（可被刷爆 AI 费用） |

- **佐证**：文件内定义的 `_require_admin()` 已无任何调用点（`rg "_require_admin"` 只命中定义行）；其余端点仅 `Depends(get_current_user)`，即**任何注册用户**（含默认 `user` 角色）都能执行上述操作。
- **附带问题**：`_require_admin()` 实现是 `user.role != "admin"`，与 `dependencies.require_admin`（admin + super_admin）不一致，即便启用也会把 super_admin 挡在外面。
- **修复建议**：统一改用 `Depends(require_admin)`；若"普通用户可维护法规"是产品决定，至少把 `bulk/abolish`、`delete`、`rebuild-index` 收回管理员，并在前端同步隐藏入口。

### P0-5 生产 4 worker 部署与"进程内状态"架构冲突【代码实证 + 实测配置】

**部署事实**：`deploy/docker-compose.prod.yml` 与根 `docker-compose.yml` 均为 `uvicorn --workers 4`（本地 `docker-compose.override.yml` 才降为 1 worker，而该文件被 `.gitignore` 忽略）。

| 进程内状态 | 位置 | 4 worker 下的后果 |
|---|---|---|
| 随机 `SECRET_KEY` | `config.py:60-68`：未显式注入时**进程内生成随机密钥** | **本轮实测修正（见 §8.5）**：同一 uvicorn `--workers 4` 进程树内的 4 个 worker 共享同一把随机密钥（40 次并发新建连接全部 200）；但**跨实例不通用**——8000 容器签发的 token 打 8001 容器 8/8 全 401。风险=横向扩容/多副本/滚动发布/双实例灰度时登录态随机失效；本地容器实测 `SECRET_KEY` 为空（root compose `${SECRET_KEY:-}`），生产 compose 用 `:?` 强制非空 |
| `_active_generations` / `_PROGRESS` / `_failed_sections` | `routers/generation.py`、`services/generation_progress.py`、`services/plan_generation_service.py` | 重复启动生成（防重失效，双倍 AI 费用 + 章节并发写覆盖）；轮询进度来自非执行 worker 时返回空，前端显示 0%/停滞；stale 判定误伤（见下） |
| `_LIVE_RA_GENERATIONS` / `_LIVE_RI_GENERATIONS` | `risk_assessment.py:50`、`resource_investigation.py:49` | 同一企业可并发启动两份报告生成，费用翻倍、写库竞争 |
| APScheduler | `main.py:142-158`：在 lifespan 内启动 interval 任务 | **4 个 worker 各起一个调度器** → 每 5 分钟隐患扫描跑 4 遍，产生重复任务/通知（现有"存在性防重"是查询后插入，存在竞态窗口） |
| 登出黑名单 `_revoked_tokens` | `auth_service.py:15`（注释已自认"多 worker 失效"） | 4 worker 下登出只有 1/4 概率真正生效，其余 worker 继续接受已登出 token |
| 限流器 `_limiter` | `middleware/rate_limit.py`（注释自认需换 Redis） | 实际阈值放大 4 倍；叠加 P1-1 后变成全站共享一个桶 |
| 外部任务表 `_external_tasks` | `routers/external.py:36` | 任务创建在 worker A、状态查询落到 worker B → 查不到任务 |
| 公开上报 nonce 缓存 `_nonce_cache` | `routers/public_hazard.py:55` | 重放防护跨 worker 失效（同一 nonce 在另一个 worker 可再次通过） |
| Mermaid 浏览器实例 / 缓存 | `services/mermaid_renderer.py` | 4 份 Chromium 常驻，内存占用 ×4 |

**典型故障链**（`generation.py:966-978`）：

```
worker A 正在生成 plan X（A 的 _active_generations[X]=True）
用户再点一次生成 → 请求落到 worker B
B 读 DB 见 status='generating'，但 B 的 _active_generations 为空
→ 判定为"stale generating"→ 把 DB status 改回 draft → 重新启动生成
→ 同一预案两份生成并发写同一批 plan_sections
```

- **修复方向（按优先级）**：
  1. 把生成状态/防重/停止信号迁到 DB 表或 Redis（最小改动：用 `plan_projects.status` 做乐观锁 + `SELECT ... FOR UPDATE`，停止信号加一列 `generation_cancel_requested`）；
  2. 调度器改为"单实例"模式（独立容器/进程跑 APScheduler，或加 advisory lock 选主），或直接改由外部 cron 调用一个内部端点；
  3. 登出黑名单、限流、nonce 迁共享存储（Redis）；
  4. 短期可先把生产回到 `--workers 1`，代价是并发能力下降——但这比当前"逻辑随机失效"更可预测。

### P0-6 敏感凭据加密使用公开默认密钥 + AES-ECB【代码实证】

- **位置**：`backend/app/services/secret_utils.py`

```python
def _derive_key() -> bytes:
    return settings.ENCRYPTION_KEY.encode()[:32].ljust(32, b"\0")
cipher = AES.new(_derive_key(), AES.MODE_ECB)      # 无 IV、无认证
```

- **默认值即公开值**：
  - `deploy/docker-compose.prod.yml:38`：`ENCRYPTION_KEY: ${ENCRYPTION_KEY:-abcdefghijklmnopqrstuvwxyz123456}`
  - `.env.example`：`ENCRYPTION_KEY=abcdefghijklmnopqrstuvwxyz123456`，并注明"**不要修改**（当前数据库中的 AI Key 使用该值加密）"
  - `config.py` 字段默认 `"a" * 32`
- **影响**：数据库一旦泄露（备份、误授权、SQL 注入、离职带走），攻击者用仓库里公开的默认串即可解密 `ai_configs.api_key_encrypted` 与 `third_party_config`（QCC/高德/PROTEGO HMAC secret）全部密文；AES-ECB 还会泄露相同明文块。
- **附**：密钥不可轮换——文档明确"改了就读不出旧数据"，说明缺少密钥版本/双写迁移机制。
- **修复建议**：① 生成随机 `ENCRYPTION_KEY` 并随部署注入（不要再给可用默认值，缺失时应 fail-fast）；② 换 AES-GCM（随机 nonce + 认证标签），或引入 KMS/密钥文件挂载；③ 增加 `key_version` 字段，支持双密钥解密→重加密轮换；④ 迁移脚本一次性重加密存量数据。

## 三、P1 高风险问题（建议 1–2 周内处理）

### P1-1 网关 nginx 配置缺 SSE 必需项，且丢失真实客户端 IP【代码实证】

`deploy/gateway-nginx.conf.example` 的 `/api/` 只有：

```nginx
location /api/ { proxy_pass http://{{宿主机IP}}:8000/api/; }
```

缺失项与后果：

| 缺失配置 | 后果 |
|---|---|
| `proxy_buffering off;`（或 `proxy_cache off`） | 系统有 **12 个 SSE 端点**（Chat ×2、预案生成 ×4、风险评估 ×3、资源调查 ×3），nginx 默认缓冲会让"逐字流式"退化为整段返回/长时间无输出 |
| `proxy_read_timeout 300s+` | nginx 默认 60s：长章节生成/长对话会被 504 掐断 |
| `proxy_http_version 1.1; proxy_set_header Connection "";` | 连接复用/分块转发不稳 |
| `proxy_set_header X-Real-IP / X-Forwarded-For` | 后端 `request.client.host` 全部等于网关 IP → **登录限流（30 次/15 分钟）变成全站共享一个桶**，注册（10 次/小时）同理；日志也失去真实来源 IP |

- **额外说明**：`uvicorn` 默认 `--forwarded-allow-ips=127.0.0.1`，即便补了 XFF 头，只要网关不是从 loopback 发起，也需要显式 `--proxy-headers --forwarded-allow-ips=<网关IP>`。
- **待验证**：以上依据仓库内网关模板；公司线上实际 nginx 配置是否已额外补齐这些项，需登录服务器核对一次（本次无法访问该公司环境）。
- **修复建议**：给出生产可用的 nginx location 模板（关闭缓冲、超时 300s+、透传真实 IP、SSE 专用 `add_header X-Accel-Buffering no`），并在 `scripts/deploy-check.sh` 里加"流式端点 3 秒内收到首个 chunk"的验证项。

### P1-2 数据库连接池上限超过 Postgres 上限【实测 + 代码实证】

- `database.py`：`pool_size=10, max_overflow=20` → 单 worker 最多 30 条
- `deploy/docker-compose.prod.yml`：4 worker → 理论峰值 **120 条**
- 实测：`SHOW max_connections;` → **100**（prod compose 未上调该参数，也无 PgBouncer）
- **后果**：高并发（含生成期间的轮询请求）会触发 `too many clients already`，表现为随机 500/超时。
- **修复建议**：worker 数 × (pool_size + max_overflow) ≤ 70；例如 4 worker 时 `pool_size=5, max_overflow=10`；或引入 PgBouncer。

### P1-4 权限模型只有"菜单级"，且种子数据不完整【代码实证 + 实测】

- `permissions` 表有 `category='menu'|'action'`，但后端**没有任何 action 权限校验**（只有 `require_admin/require_super_admin` 两个粗粒度依赖）；动作权限仅是管理界面里的展示项。
- **种子缺口（实测）**：`backend/app/seed_roles.sql` 的菜单权限列表里**没有 `menu:regulations`**，全仓仅注释提到"存量库 menu:regulations 靠手工插库"（`db_migration_data_dicts_permission.sql` 注释）。当前本地库有该权限（历史手工插入），但**全新安装按仓库脚本执行时不会生成**，结果是 `frontend/src/utils/menuMap.ts` 的门控使法规管理页对 admin/super_admin 都 403（PermissionRoute 直接拦截）。
- **越权升级**：`admin_users.create_user/update_user` 只要求 `require_admin`，但 `role` 取自请求体且仅校验"角色存在" → **普通 admin 可创建或把任意账号提升为 `super_admin`**。
- **修复建议**：① 补一个幂等迁移，把 `menu:regulations`（以及后续新菜单）纳入种子；② 后端引入 action 级权限依赖（`require_permission("regulation:write")`）；③ 提权操作（创建/修改 super_admin）限定 `require_super_admin`。

### P1-5 忘记密码链路是半成品【代码实证】

- `auth_service.send_password_reset_email()` 是空函数（`return None`），`auth.py::forgot_password` 调用它后直接返回"我们将发送密码重置邮件" → **用户永远收不到邮件**。
- 重置 token 明文存 `password_reset_tokens.token`（`String(255)`，唯一索引），无哈希、无尝试次数限制；DB/备份泄露即可直接重置任意账号密码。
- 前端桌面登录页也缺少"忘记密码"入口（9-02 报告 I6 仍然存在）。
- **修复建议**：接入 SMTP/邮件服务或明确降级为"联系管理员重置"（至少不要误导用户）；token 存哈希 + 单次使用 + 失败计数；桌面登录页补入口。

### P1-6 上传与导出目录的静态暴露面偏大【代码实证 + 实测】

- `main.py` 将 `/uploads` 直接 `app.mount(...)`，无鉴权（文件名是 uuid4 hex，猜测难度尚可，但链接一旦外泄即长期公开；含企业证照、现场照片、楼层图）。
- `/exports` 无静态挂载，但 P0-2 的下载接口等价于公开目录，且目录里现在混有开发遗留脚本（`_regen_real.py`、`_final_sample.py` 等，可被 `download_export` 的正则放行）。
- **修复建议**：静态文件统一走"带签名、带时效"的下载接口；清理 exports 中的 `_*` 开发产物并加启动期清理；给 uploads 增加按归属鉴权的代理路由。

### P1-7 内部错误信息直接回传客户端【代码实证】

- 大量 `raise HTTPException(500, f"...{e}")` / `str(e)` / `raw[:200]`：`regulations.py:284/339/495`、`generation.py:721-723`、`chat.py:588`、`export.py:410`、`hazardous_chemicals.py:244/344`、`resources_ext.py:523-527/735-739`、`resource_investigation.py:755`、`risk_assessment.py:996` 等。
- 后果：泄露内部异常细节、模型返回原文，甚至可能带出请求 URL（含 key）与文件路径；对排障也无价值（日志里已有）。
- **修复建议**：统一 `raise HTTPException(500, "生成失败，请稍后重试（错误码 X）")` + 服务端日志记录完整异常。

### P2-6 数据库迁移与全新安装路径【代码实证】

- 迁移运行器本身设计良好（advisory lock、`schema_migrations`、逐脚本事务、失败 fail-fast），这是当前工程化程度最高的部分。
- 但**"空库"与"既有库首次升级"用同一套 baseline 逻辑**：`applied` 为空且 `MIGRATE_FRESH != 1` 时，全部基线脚本被**只记录不执行**。真正的新库（schema_migrations 空）会因此跳过基线脚本里的数据种子。
- `scripts/deploy.sh` 的"一键全新安装"路径**没有设置 `MIGRATE_FRESH=1`**，且仓库不含 `deploy/docker-compose.prod.yml` 需要的 `db-init/`（注释要求部署者手工提供）→ 按文档走全新安装，得到的是一个"表建了、种子数据可能不全"的库。
- 建议：① `deploy.sh` 增加"检测到空库自动置 MIGRATE_FRESH=1"的显式分支；② 把 `seed_roles.sql` 纳入迁移体系（当前它不被任何代码执行，角色/权限种子靠手工）；③ 补 `menu:regulations` 等缺失权限种子（见 P1-4）。

### P2-7 本地 `.env` 的 QCC Key 拼接错误【实测】

- `backend/.env` 中 `QCC_API_KEY` 的值为 133 字符，实际内容是 `Bearer <keyA>` + 字面量 `` `n `` + `QCC_API_KEY_FALLBACK=Bearer <keyB>` —— 也就是把两行写成了 `\n` 的**字面量反引号写法**，导致两个变量粘成一行、`QCC_API_KEY_FALLBACK` 实际未定义。
- 后果：① 该机的 QCC 调用若走 env 兜底会发送非法 token；② 5 个 `test_third_party_config` 用例因此失败；③ key 被打印进 pytest 输出。目前数据库里的 `third_party_config` 两份 QCC 密文长度正常（各 128 hex），说明历史 seed 用的是正确值——**修复 .env 后需确认 DB 行优先于 env，避免回退到坏值**。
- 建议：修正 `.env` 为两行（或删除该行改用管理员页面配置）；在 `import_seed_configs` 里加"值含 `` `n ``/换行/Bearer 前缀重复"的格式校验并拒绝入库。

### 8.5 对前文 P0-5「SECRET_KEY」结论的修正

本轮做了交叉验证，把原先的推断改为实测结论：

| 实验 | 配置 | 结果 |
|---|---|---|
| 同一容器内 4 worker | `uvicorn --workers 4`、不注入 `SECRET_KEY` | 1 次登录签发 token，40 次并发（每次新建连接）打 `/users/me` → **200×40**；同批 40 并发企业列表 7.24s 完成（说明确实打到了多个 worker）→ **同进程树内 token 互通** |

**结论**：`SECRET_KEY` 风险不是"4 worker 之间随机 401"，而是"**多实例/多副本/滚动发布时登录态随机失效**"；同时 root compose 默认传空值（实测容器 `SECRET_KEY` 长度 0）只是被"随机生成 + 进程树内共享"掩盖了。生产 compose 的 `${SECRET_KEY:?}` 强制非空仍然是必须保留的正确设计。

## 九、LLM 供应商侧超时/限流行为（mock 供应商实测，零费用）

### 9.1 方法

在 backend 容器内起本地 mock 供应商（`ThreadingHTTPServer`），用 `llm_client` 的真实代码路径注入 6 种场景：持续 429、持续 500、401、响应超时、正常流式、**流中途断连**；逐项记录重试次数、退避耗时、最终异常类型与 HTTP 映射。

### 9.2 结果

| 场景 | 实际重试次数 | 耗时 | 结果 | 评价 |
|---|---|---|---|---|
| 持续 429 限流 | 3（默认） | 3.65s | `LLMError(429)`，退避 1s+2s | ✅ 符合设计 |
| 持续 500 | 2（max_retries=1） | 1.24s | `LLMError(500)` | ✅ |
| 401 无效 Key | **1（不重试）** | 0.01s | `LLMError(401)` → 映射"AI API Key 无效或已过期" | ✅ 防打爆 |
| 超时（timeout=1s） | 2 | 3.22s | `LLMError(status=0)` | ✅ 会重试 |
| 超时经 `llm_text_completion` | 4 | 11.85s | **`HTTPException(500)` + "AI调用失败: 0"** | ❌ 预期 504，见 B1 |
| 正常流式（3 块 + [DONE]） | 1 | 0.46s | 3 块顺序正确 | ✅ |
| **流中途断连（2 块后断开）** | 1 | 0.01s | **静默返回 2 块，success** | ❌ 见 B2 |

### 9.3 两个真实缺陷

- **B1 超时错误映射失效（死代码）**：`llm_text_completion` 里 `except httpx.TimeoutException → HTTPException(504)` 永远不会命中，因为 `_post_with_retry` 已把超时包成 `LLMError(0, ...)`；用户看到的是 500 + `AI调用失败: 0 <空消息>`，既不好排查也不符合"超时应重试/可区分"的产品语义（`llm_client.py:239-247`）。
- **B2 流式截断静默通过**：`_stream_response` 在供应商中途断开时走正常 `return`，调用方拿到半截文本并当作完整结果继续落库。对章节生成而言 = 用户得到半截正文且没有任何错误提示；对报告生成同理（`llm_client.py:184-186`）。建议：断流时抛出可识别异常或至少回传 `finish_reason`/截断标记。

## 十、并发压测（连接池 / HTTP 负载 / SSE 线程）

### 10.1 连接池上限：4 worker 必然撞 Postgres `max_connections`【实测】

| 项目 | 数值 |
|---|---|
| 应用池配置 | `pool_size=10, max_overflow=20`（`database.py`） |
| 生产 worker | 4（`deploy/docker-compose.prod.yml`） |
| DB 上限 | `max_connections=100`（实测） |
| 探针 | 4 进程 × 30 并发连接（与 app 完全相同的池参数）执行 `pg_sleep(6)`，共 120 次 |
| 结果 | **成功 70 / 失败 50**，失败全部为 `TooManyConnectionsError: sorry, too many clients already`（worker0 30/30 成功、worker1 8/30、worker2 5/30、worker3 27/30） |

**结论**：4×(10+20)=120 > 100，生产并发一上来就会出现随机 500/连接失败；建议改为 4×(5+10)=60，或引入 PgBouncer（transaction pooling）。复现：`python /app/exports/_concurrency_probe.py pool`。

### 10.2 HTTP 负载：1 worker vs 4 worker 同条件对比【实测】

端点 `GET /api/v1/enterprises?page_size=100`（该账号 118 家企业）：

| 场景 | 总耗时 | p50 | p95/max | 成功率 |
|---|---|---|---|---|
| 单请求基线 | 818ms | — | — | 200 |
| 4 并发 / 1 worker | 1.83s | ~1.8s | — | 4/4 |
| 40 并发 / **1 worker**（本地 override） | 15.55s | 9.47s | max 12.58s | 40/40 |
| 40 并发 / **4 worker**（临时容器，跑完已删除） | **7.12s** | **3.57s** | max 4.29s | 40/40 |
| 60 并发 / 1 worker | 19.63s | 17.62s | p95 19.58s | 60/60 |

**结论**：① 4 worker 相对 1 worker 只有约 2.2× 提升（DB/查询是瓶颈，不是 CPU）；② 单请求 818ms 偏慢（118 家企业 ≈ 7ms/家），更像 N+1 查询，建议对 `enterprises` 列表做 SQL 计数/慢查询 profile；③ 所有请求都成功，说明本地单机并非错误率问题，而是**吞吐与连接上限**问题。

### 10.3 SSE 与长连接线程模型【实测】

- **后端（uvicorn）**：12 个 SSE 端点全部是异步生成器，不占线程；实测直连后端流式请求 1.1s 内返回 3 条事件（`chunk/conv_id/done`）。
- **8082 自托管前端（`frontend/server.py`，ThreadingHTTPServer）**：
  - 每连接一个线程、**无上限**：实测 30 个"大文件长下载"连接保持期间，容器内 `PID1` 线程数 **31**（1 主 + 30 子），连接释放后回落；
  - 60 个空闲连接保持期间，静态页仍稳定 6–8ms（说明中等并发可用）；
- **新缺陷 N3（SSE 代理协议错乱）**：代理把后端的 `Transfer-Encoding: chunked` 响应头原样转发，却写入 `urllib` **已解码**的 body，导致严格客户端直接失败：

```
$ curl -N -D - -o NUL -X POST http://127.0.0.1:8082/api/v1/chat ...
HTTP/1.0 200 OK
Server: EmergencyPlan
transfer-encoding: chunked        ← 后端头被原样转发
content-type: text/event-stream
（curl 侧协议错误 / httpx 侧 RemoteProtocolError: peer unexpectedly closed connection）

直连 8000 同一请求：200 + 正常 3 条 SSE 事件（1.1s）
```

- **影响**：浏览器因容错仍能显示内容（本轮浏览器 Chat 实测可用），但任何严格 HTTP 客户端、企业网关二次代理、监控探针都会失败；这也是"流式体验不稳定"的结构性来源。修复：代理不要转发 `Transfer-Encoding`/`Content-Length`，或按帧重新 chunk 编码（更稳妥：自托管形态改用 nginx 托管静态 + 反代 API）。
