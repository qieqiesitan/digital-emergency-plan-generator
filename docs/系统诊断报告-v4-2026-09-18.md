## 三、本轮新发现并修复的真实缺陷

> 检出方式：摘除 `@ts-nocheck` 后 `tsc -b` 暴露 106+ 处类型错误，逐个人工判断；其中下列条目是**运行时缺陷**而非纯类型问题。部分缺陷由 v3 的浏览器验收未能覆盖（验收只验"页面能打开"，未验"表单能提交""提示有文案"）。

### P0-1 移动端新建/编辑企业无法提交（行业分类没有入口）

- 现象：`EnterpriseForm` 以"字段组件"方式使用 `SelectSheet`（只传 `label/value/options/onChange/placeholder`），但 `SelectSheet` 实际是"受控弹层"，要求 `open`/`onClose`，也没有任何触发按钮。
- 影响：`open` 恒为 `undefined` → 弹层永不渲染 → 用户无法选择行业分类；而表单校验 `if (!values.industry) e.industry = "请选择行业分类"` 会让**提交永远失败且不显示错误提示**（`error` 未渲染）→ 移动端"新建企业"整条链路死锁。
- 修复：重写 `SelectSheet` 为自包含字段组件（自带触发器 + 内部 `open` 状态 + 展示已选值 + `placeholder` 占位 + `error` 文案），并在 `EnterpriseForm` 传入 `error={errors.industry}`。
- 复验：移动端 390 实测"打开选择器 → 选工贸 → 提交成功 → toast 显示'企业创建成功' → 跳转详情页"；截图 `b1-mobile-enterprise-form.png`（可见行业分类字段与"工贸"）。

### P1-1 后端 `PUT /plans/{id}` 丢弃创作风格（前端保存无效）

- 现象：`PlanUpdate` schema 含 `style_preference` / `advanced_prompt_overrides`，但路由只执行 `if data.title is not None: p.title = data.title`。
- 影响：Web 端"创作风格"与"高级模式提示词覆盖"保存后重新打开即回到默认值（静默丢数据）。
- 修复：`backend/app/routers/plans.py` 落库两字段；新增 `backend/tests/test_plan_update_style.py`（2 例，含"只传 title 不清空已有风格"），并做**红-绿验证**（临时禁用修复 → 用例失败；恢复 → 通过）。
- 复验：浏览器实测"点'正式' → 保存 → 刷新 → 弹窗仍选中'正式'"。

### P1-2 前端只写不读：创作风格/高级覆盖回填缺失

- 现象：`PlanEditorPage` 只调 `updatePlan({style_preference})`，从未把 `plan.style_preference` 读回本地状态；前端 `PlanProject` 类型里也缺这两个字段。
- 影响：即便后端已落库，UI 仍显示默认值 → 用户以为"保存失败"（本轮 E2E 首跑正是因此失败，暴露了这一层）。
- 修复：`types/plan.ts` 补 `style_preference` / `advanced_prompt_overrides` 声明；`PlanEditorPage` 增加渲染期回填（含 `mode=advanced` 时恢复高级模式）。

### P1-3 移动端 23 处 toast 调用签名错误（提示条变空白）

- 现象：`showToast("企业已删除", "success")` 等位置参数写法（8 个文件 23 处），而 `useToast().showToast` 接收 `{ type, message }`。
- 影响：运行时把字符串当 options 展开 → 弹出一条**无文案、无颜色**的空白提示条（成功/失败反馈全部丢失），且 `danger` 不是合法类型。
- 修复：23 处改为对象调用（`danger` → `error`）；后续 `useToast` 拆到独立模块后类型可直接校验。
- 复验：移动端创建企业后实测 toast 文案"企业创建成功"可见。

### P1-4 移动端输入框 onChange 签名错误（输入即抛错）

- 现象：`Input` 组件回调签名是 `(v: string) => void`，但 `ChangePasswordScreen`（3 处）与 `ProfileScreen`（1 处）写成 `(e) => setX(e.target.value)`。
- 影响：输入时 `e.target` 为 `undefined` → 抛 TypeError，受控值不更新 → **移动端修改密码/改姓名不可用**。
- 修复：改为 `onChange={setX}`。
- 复验：移动端 390 实测两个密码框输入后 `input_value()` 与输入一致。

### P1-5 空态按钮传参错误（按钮无文案/点击报错）

- 现象：8 处把 `EmptyState` 的 `action` 传成字符串 + `onAction`（`action="创建企业"`），组件实际要求 `action={{ label, onPress }}`。
- 影响：空态主按钮渲染为无文案按钮，`action.onPress` 为 `undefined`，点击无效（新建企业/新建预案/重试等引导入口失效）。
- 涉及：`EnterpriseListScreen`、`PlanCardsScreen`（2）、`ResourceListScreen`、`ResourceInvestigationScreen`、`RiskAssessmentScreen`、`DashboardScreen`、`EnterprisePlanListScreen`。

### P1-6 移动端预案编辑器本地草稿写入垃圾数据

- 现象：`addDraft(planId, sectionKey, content)` 位置参数调用，而 store 签名是 `addDraft({ planId, sectionKey, content, updatedAt })`。
- 影响：草稿条目字段全部 `undefined`，store 里出现无效草稿（"保存失败已暂存本地草稿"的恢复链路不可靠）。
- 修复：改为对象调用，补 `updatedAt: Date.now()`。

### P1-7 移动端企业详情"应急资源"永远为空

- 现象：`listResources()` 返回 `ApiResponse` 包装（`{code,message,data:{items}}`），页面却读 `resources?.items`；且列表项字段用了不存在的 `res.type`（应为 `res.category`）。
- 影响：详情页资源 Tab 恒显示"暂无应急资源"，统计口径误导。
- 修复：改读 `resources?.data?.items`，字段改 `res.category`。

### P2-1 antd v6 `Divider` 属性失效（权限分组标题不左对齐）

- 现象：`<Divider orientation="left">`——v6 的 `orientation` 只接受 `horizontal|vertical`，文本位置改用 `titlePlacement`。
- 修复：改 `titlePlacement="start"`（2 处）。

### P2-2 法规图谱力导布局随机 + 渲染期读 ref

- 现象：`RegulationGraph` 用 `Math.random()` 初始化节点位置，并把 `simNodes/simEdges` 存在 ref、在**渲染期读取**（同时还存在渲染期写 ref：`panRef.current = pan`）。
- 影响：每次数据/筛选变化都重新随机布局（视觉跳变）；ref 变化不触发重渲染，交互态（拖拽光标）不同步。
- 修复：哈希派生确定性初始位置；布局计算移入 `useMemo`（纯计算）；拖拽状态改用 state；新增 2 个 effect 同步 wheel 监听所需的 `pan/zoom` ref。

### P2-3 富文本"AI 重写"上下文可能过期

- 现象：`RichTextEditor` 在渲染期读 `editorRef.current.state.doc` 计算 `contextBefore/After`（ref 变化不触发重渲染）。
- 修复：上下文改由 `onSelectionUpdate` 写入 state，渲染期只读 state；`editorReady` 用 state 取代 ref 判断。

### P2-4 移动端 AI 生成弹窗风格参数未传递

- 现象：`onGenerate(selectedChapters)` 少传第二个参数 `styleParams`，同时 `DEFAULT_MOBILE_STYLE` 未被使用（死常量）。
- 修复：按选择映射 `detail_level` 后传递 `{...DEFAULT_MOBILE_STYLE, detail_level}`。

### P2-5 法规更新接口类型过严 / 风险等级 `as any`

- `updateRegulation(id, data: RegulationCreateRequest)` 让"只提交被编辑字段"的调用报错（靠 `@ts-nocheck` 掩盖）；后端实现是增量更新（`parsed.get(...)` 取默认值）→ 参数改为 `Partial<RegulationCreateRequest>`。
- `RiskSourceForm` 的风险等级渲染 `level={v as any}` → 收口为 `RiskLevel` 联合类型。

### P2-6 源码卫生：34 个前端 + 16 个后端源文件带 UTF-8 BOM

- 影响：BOM 会让补丁/工具按字节匹配失败（本轮 `Toast.tsx` 就因 BOM 导致补丁无法套用），历史事故同源。
- 修复：移除全部 50 个文件 BOM（逐字节保留其余内容）；`frontend/scripts/check-source-hygiene.mjs` 现已覆盖 `frontend/src` + `backend/app|tests|scripts`（835 文件），接 CI 阻塞步骤 + `npm run check:hygiene`；后端守护测试 `test_frontend_sources_have_no_bom` 同步扩展。

### P2-7 报告预览页 404 未处理 rejection（控制台报错噪音）

- 现象：`RiskAssessmentPreview` / `ResourceInvestigationPreview` 首屏加载写的是
  `getXxxPreview(id).then(setData).finally(...)`——**缺 `.catch`**；报告尚未生成时后端返回 404，
  于是产生 "Request failed with status code 404" 的未处理 rejection（页面本身仍显示空态）。
- 影响：正常业务路径在浏览器控制台/前端错误监控里表现为异常，掩盖真实错误。
- 修复：两处补 `.catch(() => setData(null))`（保持空态语义）。
- 复验：广域冒烟中这两个页面 `pageerror` 由 1 变 0，仅剩浏览器对 404 响应的网络日志。

### P3-1 4 处乱码注释

- `PlanCardsScreen` 中 4 条注释为 GBK 误解码产物（如 `// 鏃犱紒涓?`），已按上下文还原为中文。

### P3-2 后端 166 处未使用导入（F401 债务）

- 现象：`pyproject.toml` 显式 `ignore = ["F401"]`，注释写明"当前 119 处…逐模块清理"——W3 遗留的未结项；实际规模已涨到 **175 处**（app 119 + tests 56）。
- 影响：死导入掩盖真实依赖关系；也解释了历史上"自动删除转出口导入会静默破坏调用方"的踩坑。
- 处理方式（先保护、再清理）：
  1. 把真正的**转出口**显式化：`app/models/__init__.py` 增加 `__all__`；`app/services/risk_notice_card_data.py` 改为 `import X as X` 冗余别名（该模块的 `LEVEL_COLORS` 被 `app/routers/risk_notice_card.py` 直接导入使用）。

## 三之二、B3：同类潜在缺陷审计（后台任务与定时器）

> 检出方式：按"同类根因扫全仓"——`asyncio.create_task`、`setInterval`、`_background_tasks`、`Promise.resolve().then` 四条线索逐一核对。共 5 项。

### P1-8 后台任务"创建即丢弃"（GC 隐患 + 异常静默）

- 现象：`app/routers/external.py` 的外部对接生成任务 `asyncio.create_task(...)` **返回值没有保存**。
- 影响：asyncio 官方明确要求保存返回值，否则任务可能执行到一半被垃圾回收；异常也只会变成

### P2-9 三处 `_background_tasks` 引用表只增不减（内存泄漏 + 异常不可见）

- 现象：`routers/generation.py`（2 处）、`services/plan_generation_service.py`（1 处）、`services/workflow/runner.py`（2 处）把任务存进 `dict[str, Task]`，**全仓无任何读取**（唯一一次 pop 只覆盖一个分支），且 dict 只增不减。
- 影响：完成的任务对象（含 traceback、返回值）随生成次数累积；任务异常同样不落日志。
- 修复：删除 3 个 dict，6 处统一改为 `spawn(..., name="plan-generate:<id>" 等)`；注册表在完成回调里 `discard` 并记录异常。

### P2-10 流式生成的 producer 失败会静默结束 SSE

- 现象：`app/services/background_stream.py` 的 relay 任务只把事件转发给队列，producer 抛错时消费端只会看到"流正常结束"。
- 修复：relay 任务改用 `spawn(..., name="background-stream")`，失败必进日志（协议行为不变，避免改动 SSE 契约）。

### P2-11 移动端导出轮询定时器无卸载清理

> 动机：4 项外部待办（密钥轮换 / 网关配置 / 升级演练 / 坏密文）此前只能"人肉照手册做"。

### P0-2 空库全新安装启动失败（演练实测，7 个根因）

在独立 project 的空库上按 `MIGRATE_FRESH=1` 跑到启动，依次撞到并修复：

| # | 现象（演练原文） | 根因 | 修复 |
|---|---|---|---|
| 1 | `relation "chat_messages_seq" does not exist`（create_all 阶段） | 模型用裸文本 `nextval('chat_messages_seq')` 作 server_default，**没有任何地方创建该序列** | 模型改用 `Sequence("chat_messages_seq")`；新增幂等迁移 `db_migration_20260919_chat_messages_seq.sql` 补建并对齐 `setval` |
| 2 | `null value in column "is_enabled" of relation "ai_capabilities"` | 模型只有 ORM `default`，`create_all` 建表没有库级默认值；种子里也漏列 | 模型补 `server_default`；`db_migration_20260917_ai_capability.sql` 的 8 行种子显式写 `is_enabled/allow_manual` |
| 3 | `null value in column "validation" of relation "work_ticket_template_fields"`（217 条种子） | 同上（`validation` 只有 ORM default） | 模型补 `server_default='{}'::jsonb`（一处修好 217 条种子） |
| 4 | `null value in column "enabled" of relation "data_dicts"` | 同上 | 模型补 `server_default=true` |
| 5 | `null value in column "id" of relation "data_dicts"` / `hazard_checklist_templates` | 种子 INSERT 不写主键，而模型只有 ORM `uuid4`、无库级默认 | 模型补 `server_default=gen_random_uuid()`（PG13+ 内置） |
| 6 | `A value is required for bind parameter '0'`（`data_dicts` 种子） | 迁移执行器用 `text(statement)`，把 JSONB 里的 `{"factor":0.5}` 的 `:0` 当成绑定参数 | `migration_runner._apply_script` 改用 `exec_driver_sql`（裸 SQL 原样下发） |
| 7 | `function gen_random_bytes(integer) does not exist`（notice_card 迁移） | 依赖 pgcrypto 扩展，全新库未安装 | 改用内置组合 `encode(uuid_send(gen_random_uuid()),'hex')×2` = 32 随机字节 / 64 hex，零扩展依赖 |

**存量库一致性**：历史库（如本机开发库）的 `chat_messages.seq` 默认值实际是早期
`create_all` 自动生成的 `chat_messages_seq_seq`，与模型里写的 `chat_messages_seq` 并不一致。
修复迁移同时做两件事：补齐 `chat_messages_seq` 并把当前值 `setval` 到 `MAX(seq)`、
`ALTER COLUMN seq SET DEFAULT nextval('chat_messages_seq')` 统一默认值。
**实测（本机开发库）**：迁移后 `schema_migrations=51`、列默认值变为 `nextval('chat_messages_seq')`、
新插入的 `seq=306`（接续原最大值 305），插入链路正常。

**影响面**：这 7 个点位的共同后果是——**新服务器上从空库装 0.3.x 根本起不来**（旧库升级因为
表已存在、迁移已记账而侥幸不触发）。这也解释了为什么"升级包实机演练"一直是必须做但没做的一步。

**永久守护**：

- `backend/tests/test_model_sequence_defaults.py`：任何 `nextval('X')` 默认值都必须有 `Sequence` 声明（红-绿已验证：改回旧写法即失败）；

## 三之八、B9：备份/回滚链路纳入演练（升级失败时真能退回去）

> 升级包最怕的不是"装不上"，而是"装坏了退不回来"。此前 `backup.sh` / `rollback.sh`
> 只在手工场景跑过，且**容器名写死**、回滚必须人工输入确认，无法在隔离栈上自动演练。

### 改动

1. **脚本参数化（保持生产默认行为不变）**
   - `backup.sh`：支持 `DB_CONTAINER`（默认 `emergency-plan-db`）与 `BACKUP_DIR`（默认 `backups`）；
   - `rollback.sh`：支持 `DB_CONTAINER` / `BACKEND_CONTAINER` / `BACKUP_DIR`，
     并支持 `ROLLBACK_CONFIRM=ROLLBACK` 非交互确认（**不传则仍是人工输入 ROLLBACK**，安全默认不变）。
2. **演练新增 DR 步骤（5b）**：写入 `sys_config.rehearsal_canary` 标记行 → 调 `backup.sh` →
   删除标记行模拟"升级把数据搞坏" → 调 `rollback.sh` → 断言标记行恢复 + 后端健康 200 →
   清理标记行。全程指向 `ep-rehearsal-*` 容器。
3. **防误操作护栏**：演练里先解析容器名，**必须匹配 `ep-rehearsal-*` 才继续**——
   否则 `backup.sh`/`rollback.sh` 的默认值会指向生产容器（这条护栏是在调试本步骤时补的：
   第一版脚本因 `sys_config.config_type` 非空、标记行插入失败而静默退出，暴露了"默认值落到生产"的风险面）。

### 实测证据

- 隔离栈演练：**15/15 PASS**（备份 dump 452K → 删除标记行 → 回滚 → 标记行恢复 → 健康 200）；
- 生产默认路径回归（真实开发栈）：`backup.sh` 产出 7.2MB dump + 18MB 文件归档；
  `rollback.sh` 全链路输出"回滚完成，后端已就绪"，回滚前后
  `schema_migrations=53 / roles=3 / permissions=20 / prompt_templates=74 / enterprises=192` 完全一致，
  接口烟测 112 端点 0 个 5xx。

### 仍需注意

- `rollback.sh` 的 `--clean --if-exists` 会**先删对象再重建**：回滚期间后端必须停止（脚本已做），
  且回滚包里必须含目标版本的全部迁移（本仓库已把 53 个迁移随包发布）。
- 文件资产恢复依赖部署目录结构（`backend/uploads`、`backend/exports`）：从"新解压目录"执行回滚

## 五、必须说明的工程折衷（3 处微任务排期）

`react-hooks/set-state-in-effect`（React Compiler 规则）会**穿透到 effect 里调用的组件内 `useCallback`**，即使函数体第一步就是 `await`：实测"内联 async IIFE / `.then` 回调"允许，"调用组件内 useCallback"报错。

因此有 3 处采用"把启动动作排到微任务"的写法（现已收敛到 `frontend/src/utils/afterCommit.ts` 单一入口，注释写明触发场景与边界），让 state 更新发生在 effect 同步阶段之外：

1. `ReportWorkspace`：`void Promise.resolve().then(() => loadDocument())`
2. `PlanEditorPage` 自动触发生成：`void Promise.resolve().then(() => startRealtimeGeneration(...))`
3. `WorkbenchCanvas` 工具切换清理：`void Promise.resolve().then(() => {...setters...})`（这些 setter 内部同时写 ref，渲染期调用会被 `refs` 规则判为读 ref）

**这不是行为等价之外的"藏问题"**：三处副作用与原先完全相同，只是延后一个微任务；若后续 React 编译规则收紧边界，这 3 处应优先重写为"事件处理器/状态机驱动"，而不是继续堆微任务。
