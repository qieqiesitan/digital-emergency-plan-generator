## 一、目标定义

### 1.1 新主线定位

一句话：**不是做"更全的安全生产台账"，而是做"AI 帮你把台账写出来、帮你判断合不合规"的安全生产管控平台。**

预案生成不再是主线，而是平台内的一个模块（"预案与应急管理"），继续作为 AI 价值的展示窗口。

### 1.2 目标模块树（以企业为单位的 13 个模块）

### 1.3 目标能力清单

**用户明确要做的 5 项**：①重大危险源台账 + R 值法分级　②风险点/分析单元/管控措施　③隐患排查治理闭环　④数据对接总线（外部数据源适配层）　⑤作业票（8 类 + 审批流）

**新主线必需、但用户清单没列的 3 项**：

- **AI 能力中台化**：现在 AI 散落在各模块的 service 里，新主线要求"深度融合"，需要统一入口与可观测性（见 4.2）
- **平台级总览（集团/多企业视角）**：从"单企业工具"到"平台"，需要跨企业聚合
- **预案与管控数据的双向打通**：风险/隐患数据要能驱动预案更新，预案要能反哺检查项

### 2.6 法规能力面

- 内置法规文本 **160+ 份**。**注意命名有两套，且体积差异极大**：
  - `texts/*.md` 里有一批是**摘要卡（1KB 以内）**，例如 `gb18218_2018.md` 仅 544 字节、`gb30871_2022.md` 仅 595 字节，**不是原文**；
  - 真原文在 `reg_*` 命名的文件里：`reg_gb_18218_2018.md`（9.4KB，含式(1)(2)、表3/表4/表5/表6）、`reg_gb_30871_2022.md`（63KB，完整）

  > ⚠️ **2026-09-17 更正**：本清单初版写成"法规库已内置 GB 18218 与 GB 30871 原文"，属**过度乐观**。经逐文件核对：原文确实在 `reg_*` 文件里，**但 GB 18218 的"表 1 / 表 2"（危险化学品临界量清单）在提取文本中缺失**——正文只写了"临界量按表1和表2确定"，表格本体没有落进 markdown（疑似原 PDF 中是图片/表格，提取时丢失）。
  >
  > 直接影响：**R 值法的 Q 值（临界量）必须另行数据化，不能指望从现有法规文本里直接取。** 这一条已加入 P0 的第 0 项任务。

  已核实**完整可用**的 GB 18218 内容（来自 `reg_gb_18218_2018.md`）：
  - 辨识指标 **式(1)**：`s = q1/Q1 + q2/Q2 + … + qn/Qn ≥ 1`（多品种时）
  - 分级指标 **式(2)**：`R = α × Σ βi × (qi/Qi)`（公式本体为图片，但全部参数与系数表完整）
  - **表3** 毒性气体校正系数 β（14 种：CO=2、氨=2、氯=4、硫化氢=5、碳酰氯=20 …）
  - **表4** 未列举危险化学品 β（按危险性类别 J1~J5、W1.1~W11 取值，1~4）
  - **表5** 暴露人员校正系数 α（≥100人=2.0、50~99人=1.5、30~49人=1.2、1~29人=1.0、0人=0.5）
  - **表6** 分级标准（一级 R≥100、二级 50≤R<100、三级 10≤R<50、四级 R<10）
  - 4.2.2 实际存在量按**设计最大量**确定；4.2.3 混合物处理规则；附录 A 辨识流程
  - **缺失**：表1（具体品种临界量）、表2（按危险性类别的临界量）
- 另有 `reg_gb_t_33000_2025`（安全生产标准化）、`reg_gb_t_29639_2020`（应急预案编制导则）、`aq3013_2008`、`reg_gb_t_13861_2022`、GB 39800 全 12 部分、`policy_hazard_investigation_2008`（隐患排查治理暂行规定）等
- 能力：`regulations/retriever.py`、`scorer.py`、`article_index.py`、`section_topics.yaml`、`graph.json`（条文知识图谱），前端 `/settings/regulations`

## 四、重复建设风险清单（红线）

以下事情**不要做**，做了就是重复建设或推倒重来：

1. **不要重做风险分级管控模块。** `risk_management.py` 76KB / 55 端点 / 7 个前端页面已成型；重做等于丢掉四色图工作台、四色图图片识别、告知卡、公示 token 这些对标系统都没有的能力。要做的是**加关联字段**。
2. **不要重做隐患排查治理闭环。** `hazard_management.py` 102KB / 36 端点 / 10 张表 / 状态机 / 角色门控 / 定时扫描 / 双导出 已成型，且已有 8 个 AI 端点。
3. **不要新建"数据中台"式总线框架。** `file_parser` + `onboarding_service` + `enterprise_knowledge_service` + `third_party_config` 已覆盖"文件解析 / LLM 抽取 / 向量检索 / 密钥管理"。只补"数据源注册 + 映射 + 同步 + 对账"这一层薄适配。
4. **不要引入 Flowable / Camunda 等 Java 工作流引擎。** 与 Python 栈不匹配、运维翻倍、AI 难介入。8 类作业票流程本质是"固定模板 + 少量条件分支"，自研轻量状态机即够（隐患状态机已是现成范式）。
5. **不要用 AI 算 R 值。** 计算必须确定性代码 + 对照 GB 18218 算例单测；AI 只做资料抽取与报告初稿。
6. **不要一次做 8 类作业票。** 先动火 + 受限空间跑通骨架（模板 → 申请 → 气体检测 → JSA → 逐级审批 → 签字 → 有效期/延期 → 废票 → 归档），再横向复制。
7. **不要砍掉预案生成。** 它是唯一的差异化资产，且重大危险源/风险/隐患正好是预案编制依据，天然打通。
8. **不要照搬对标系统的界面、字段命名与表单布局。** 无源码、无授权，按国标自研才安全；交互与信息架构必须走自己的风格。

## 六、结论

1. **清单的 ②③ 应改写为"差距补强"，不是"新建"。** 现状已覆盖目标能力的约 60%，其中风险与隐患两块是**优于对标系统**的资产。
2. **真空白只有两块：重大危险源（含 R 值法）与作业票（含审批流）**，加上一层薄的数据接入适配层。
3. **最大的隐性资产是法规库 + AI 链路。** GB 30871 真原文（63KB）与 GB 18218 的计算规则、系数表（表3~表6）均已入库且有条文精准匹配，意味着新模块从第一天就能做到"每个字段、每条措施可溯源到法规条文"——这是对标系统做不到的，也是新主线的差异化根基。**但要扣掉一项：GB 18218 的临界量清单（表1/表2）不在库里，必须另行数据化，这是 P0 的起点而不是已有条件。**
4. **最大风险不是工程量，而是定位漂移**：若按原清单从头做，会把已有的 178KB 后端路由与 13 个前端页面变成沉没成本；若持续加功能而忘了"AI 干活"的定位，会退化成又一个普通台账平台。
