## 二、本轮新修问题（4 项）

### N-1（P1）作业票并发开票撞唯一约束 → 6/8 请求 500【实测复现 → 修复 → 复验】

**现象与复现**（探针 `output/playwright/e2e-20260918/scripts/_work_ticket_code_race_probe.py`）：

```
login 200
status distribution: {200: 2, 500: 6}
distinct codes: 2 duplicates: none
FAIL: 2/8 ok

# 后端日志
sqlalchemy.exc.IntegrityError: ... UniqueViolationError:
duplicate key value violates unique constraint "uq_wti_ent_code"
```

**根因**：`app/services/work_ticket_service.py::open_ticket` 的 docstring 写着"编号冲突时重试，最终由数据库唯一约束兜底"，但实现是「查询当日同前缀编号取 MAX(seq)+1 → 单次 `flush()`/`commit()`」——**既没有重试循环，也没有加锁**。4 个 uvicorn worker 下，两名审批人/用户同时开票即命中竞态：后写入者撞 `(enterprise_id, code)` 唯一约束，异常直接冒到全局处理器变成 500，用户看到"Internal Server Error"且票没建成。

**修复**（`work_ticket_service.py:150-155`）：发号前对**企业行**加行锁，把「读 MAX(seq) → 插入」临界区串行化。

```python
# 并发发号保护：同一企业内「读 MAX(seq) → 插入」必须串行，否则并发开票会撞
# uq_wti_ent_code 唯一约束（实测 8 并发 → 6 个 500 而非重试）。
# 锁粒度=单企业行，持锁时间=一次 seq 查询 + INSERT，不影响其他企业。
await db.execute(
    select(Enterprise.id).where(Enterprise.id == enterprise_id).with_for_update()
)
```

回归守护：`backend/tests/test_work_ticket_binding.py` 断言开票路径的第一条语句必须含 `FOR UPDATE`；测试替身的 `side_effect` 同步补齐锁查询。

**复验**：同一探针修复后 `status distribution: {200: 8}`、`distinct codes: 8 duplicates: none`（PASS）。定向单测 `test_work_ticket_*` 15 passed；全量 `pytest 1908 passed`；探针产生的 10 张草稿票已按编号前缀清理（`DHZY-RACE-%`，残留 0）。

**影响面**：多审批人协作、移动端弱网重试、用户双击"开票"都会触发；数据本身没被写坏（唯一约束挡住了重复编号），但交互层面是"点了没反应 + 500"。

### N-2（P2）`backend/.env` 的 QCC 两行配置被写成一行（v1 P2-7 闭环 + 代码护栏）

**取证**（不打印密钥本体）：

```
value_len=133  space_idx=[6, 84]  token_lens=[6, 77, 48]
形状 = "Bearer <keyA>" + 字面量 `n + "QCC_API_KEY_FALLBACK=Bearer <keyB>"
```

即：本意是两行（主 key + 备用 key），实际被写成了一行、并把换行写成了**字面量 `` `n ``**。

**影响判定**：容器栈**不受影响**——容器内没有 `/app/.env`（compose 通过环境变量注入），且数据库 `third_party_config` 里已有两个 key（DB 优先于 env）；但**宿主机直跑 uvicorn**（`cd backend && uvicorn app.main:app`）会从 `.env` 读到这串畸形值，`headers={"Authorization": api_key}` 把 133 字符的脏串原样发给企查查 → 必然鉴权失败，且表现为"配置了却用不了"，很难排查。

**修复**：逐字节手术替换（其余行、行尾风格保持原样）——

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 键数量 | 1 个（`QCC_API_KEY` 含第二行内容） | 2 个（`QCC_API_KEY` / `QCC_API_KEY_FALLBACK`） |
| 值长度 | 133（含 2 个空格与 1 个反引号） | 55 / 55（`Bearer ` + 48） |
| keyA/keyB 指纹 | — | **与修复前一致**（未改密钥内容） |
| 反引号残留 | 1 | 0 |

`python-dotenv` 重新解析确认：`QCC_API_KEY len=55`、`QCC_API_KEY_FALLBACK len=55`、其余 7 个键不变。备份：`output/evidence-env-20260918/backend.env.bak-before-qcc-fix`。

**同类护栏**（`app/services/third_party_config.py:19,53-60`）：env 取值若命中 `[A-Z][A-Z0-9_]{4,}=`（把另一个环境变量赋值黏进了值里），记 `warning` 并按"未配置"处理，避免把畸形串当密钥发出去；补 2 例单测（黏行被拒 + 合法 base64/小写密钥不误伤）。`.env.example` 增补：值是**完整 Authorization 头（带 `Bearer ` 前缀）**、两个 key 必须各占一行。

### N-3（P0-1 复核）8082 静态服务器路径穿越：已修复，且无法复现

复核命令（正确姿势必须是 `--path-as-is`，否则客户端会先规范化掉 `..`）：

```powershell
curl.exe -s --path-as-is -o NUL -w "%{http_code} %{size_download}" "http://localhost:8082/../server.py"
```

10 种 payload 结果（含 `/..%2f..%2f..%2fetc%2fpasswd`、`/%252e%252e%252fserver.py`、`/..%5cserver.py`、`/dist/../server.py`、`/assets/%2e%2e/%2e%2e/server.py`、`/..;/server.py`）：

| 观察点 | 结果 |
| --- | --- |
| `/`（基准） | 200 / **842 字节** |
| 所有"看起来像穿越"的路径 | 200 / **842 字节**，或 404 / 330 字节 |
| 842 字节响应体的 SHA256 | `8bd4ccd4a3fa0877087ccb96264eb2ae4316a304b01dd5b491399ab546441069` = `/app/dist/index.html` |
| `/../server.py`（真实穿越写法） | **404**（`SimpleHTTPRequestHandler` 规范化后落到 dist 内不存在的文件） |
| 响应体里是否有 `BaseHTTPRequestHandler`/`ThreadingHTTPServer` 特征串 | **无** |
| `/etc/passwd` 内容 | **未泄露** |

**结论**：v1 P0-1 记录的"200 + passwd 内容"在当前代码上已不可复现；现在返回 200 的路径都是 **SPA 兜底**（把未知路径回落到 `index.html`，与 `/` 返回同一份字节），这是预期行为而非漏洞。W0 的修复（`frontend/server.py` 里 `os.path.realpath` 规范化 + 目录包含性校验，`528275b`）在生效。

### N-4（P3）`test_task_registry` 用例隔离缺陷（全量套件曾出现 2 failed）

**现象**：全量跑 `pytest tests` 时 2 条失败（`assert active_task_count() == 1` 实际 `6 == 1`），单独跑该文件则全绿。

**根因**：`task_registry._tasks` 是**进程级全局集合**；其他用例在各自"跑完就关闭"的事件循环里调用了 `spawn()` 且未等待完成，done-callback 不会触发 → 残留项污染了绝对值断言。属测试隔离问题，**不是产品缺陷**（生产环境每个 worker 只有一个常驻事件循环）。

**修复**：断言改为**增量**（`before` / `before + 1` / `before`），用例间互不干扰。复跑：`pytest tests -q` → **1908 passed**。
