# 数据互联互通诊断（2026-09-20）

**问题**：每个企业的每种数据，是否只填写一次即可？有没有重复填写、填了不生效的问题？
**方法**：字段级重叠扫描（全模型列名交叉比对）→ 追写入路径（42 个路由文件、195 个 POST/PUT/PATCH 端点全量列表）→ 追消费路径（生成上下文组装器、报告服务、质检、导出、聊天工具）→ **用真实数据库验证**（含一个决定性探针）。

---

## 一、结论先行

**整体评价：主要数据域已经实现"录一次、多处用"，不存在要求用户把同一份数据从头再录一遍的设计。但存在 2 处"同一事实两份来源"，其中 1 处已在真实数据上造成不一致；另有一条链路是"数据显示有、生成读不到"。**

| 数据域 | 单一事实源 | 自动流入生成/报告 | 判定 |
| --- | --- | --- | --- |
| 企业基本信息 | ✅ `enterprises` 单表（预案表只存外键，零冗余） | ✅ 章节生成 + 两份报告 + 各类 AI 引导 | **良好**（表单里 6 个自由文本主题字段与专表语义重叠，见 D-2） |
| 组织架构（人员） | ✅ `enterprise_members` 单表（节点树 `org_structure` JSON + 任职 `member_positions`） | ✅ 作业票审批人、隐患报表部门列 | **良好**（应急组织只引用 `member_id`，人不重复录） |
| 应急组织 | ✅ `emergency_org_units/roles/assignments` 三表 | ✅ 预案组织章节、组织架构图、导出签名 | **良好**（与公司组织架构是两套**结构**，属设计取舍，非数据重复） |
| 风险 | ⚠ **双模型**：旧 `risk_sources` + 新五层 `risk_zones/objects/units/events/measures` | 生成/报告/聊天/完成度 = **新五层**；计数与导出质检 = **旧表** | **有问题**（D-1） |
| 危化品 | ⚠ **双源**：`enterprises.hazardous_chemicals`（自由文本）+ `hazardous_chemicals`（台账表） | 台账 → 章节/资源报告/风险事件/重大危险源；文本 → 章节/风险 AI 引导/周边 AI | **有问题**（D-2） |
| 应急资源 | ✅ `emergency_resources` 单表（表单/AI/导入/批量四通道同一落点，内外部同表） | ✅ 资源调查报告 + 预案资源章节 + 导出质检 | **良好** |
| 周边环境 | ✅ `enterprises.surrounding_info` 单字段（表单 + AI 两个编辑器写同一字段） | ✅ 章节生成 + 两份报告 | **良好** |
| 平面图 | ⚠ 镜像双存：`enterprises.floor_plan_url` ↔ 默认楼层 `enterprise_floors.floor_plan_url` | 四色图/报告读楼层；预案疏散图优先楼层、回退企业字段 | **潜在风险**（D-4，当前数据一致） |
| 预案 | ✅ `plan_projects` 只存自身属性（类型/编号/版本）+ `enterprise_id` 外键 | ✅ 生成时组装企业上下文 | **良好** |
| 事故类型 | ✅ 后端 `accident_types.py` 唯一事实源（注释明确「禁止再散落硬编码」）+ 前端镜像常量带单测 | ✅ 风险事件/告知卡/迁移共用 | **可接受**（D-6，跨端两份常量） |

## 二、逐项问题

### D-1（P1，已真实发生）风险双模型：数据显示有，生成读不到

**事实链**：

1. 生成侧的唯一数据源是**新五层**：`services/risk_context_builder.build_risk_sources(zones)`（第 60 行）由「分区→对象→单元→事件」组装出 `risk_sources` 列表，喂给章节生成、风险评估报告、资源调查报告、聊天上下文、完成度计算；**没有任何旧表兜底**。
2. 计数侧仍在读**旧表**：`routers/dashboard.py:18`（仪表盘 `risk_source_count`）、`routers/enterprises.py:83`（企业列表 `risk_sources_count=len(e.risk_sources)`）。
3. 质检测在**旧表**：`routers/export.py:366` 与 `:470` 传 `has_risk=bool(enterprise.risk_sources)`；`services/plan_quality_service.py:368` 据此决定是否执行 E3「资源数量为 0」告警 → 对只有新五层数据的企业，**这条告警静默不触发**（漏检，不误报）。

**决定性证据（真库探针，只读）**：`output/playwright/e2e-20260918/scripts/_risk_context_vs_legacy_probe.py`

```
企业                          旧表行数   生成上下文条数
西安宝岳空间科技有限公司              12            34
陕西宝岳测绘有限公司                   7             0   <<< 旧表有数据但生成读不到
```

→ **陕西宝岳测绘有限公司**：界面上有 7 条风险源，AI 生成预案/报告时**读不到任何一条**。这不是理论风险，是当前库里的实际状态。

**存量数据**：`risk_sources` 共 19 行 / 2 家企业，其中 **13 行未迁移**（宝岳测绘 7、宝岳空间 6）。
**已有缓解措施**（做得好）：`RiskManagementTab.tsx:375` 会显示「检测到 N 条旧版风险源数据未迁移 → 迁移旧风险源」，走 `POST /risk-management/migrate-preview` + `migrate/execute` 迁移到新五层，**不需要重新录入**。
**残留问题**：迁移提示只在风险工作台里出现，而「风险源」这个 KPI 在所有页面都直接显示旧表数字；用户不点迁移就长期处于"两个数字互相矛盾"的状态。

### D-2（P1，已真实发生）危化品两份来源，且已经互相矛盾

同一件事有两个可编辑入口，且**不同 AI 路径各看一份**：

| 来源 | 存储 | 谁在消费 |
| --- | --- | --- |
| 企业档案「危险化学品」自由文本 | `enterprises.hazardous_chemicals`（Text，schema 限 2000 字） | 章节生成（`generation.py:535`）、风险 AI 引导（`risk_management.py:1290`）、周边环境 AI（`surrounding_ai.py:145`）、资源调查报告（`resource_investigation_service.py:97`） |
| 危化品台账（结构化明细，25 列，含 CAS/闪点/储量/应急处置等） | `hazardous_chemicals` 表 | 章节生成的 `chemicals` 明细（`generation.py:543`）、风险事件关联（`risk_events.chemical_id`）、重大危险源单元品种（`ledger-link`）、台账 AI 去重 |

**两个 AI 视图互不可见**：台账 AI 引导（`hazardous_chemicals.py:190-215`）只喂企业画像 + 已录台账；风险 AI 引导只喂那段自由文本。所以"AI 问的问题"和"AI 写进预案的危化品"可能基于两份不同事实。

**真实数据已矛盾**：

```
企业                          档案文本   台账行数   台账品种
西安宝岳空间科技有限公司              "无"        2   次氯酸钠溶液/乙醇（酒精）
延长壳牌石油有限公司（西安明光路加油站） (空)       24   乙醇/液化石油气/甲醇/…（24 种）
```

→ 宝岳空间：企业档案写「无」危险化学品，台账里有 2 个品种。一个用户会看到两种答案。

### D-3（P2）章节「数据依赖」已落库，但零消费 → 缺"数据变了要重生成"的提示

`plan_sections.data_dependencies` 已按模板回填（真库实例：`["risk_sources"]`、`["risk_sources","emergency_resources"]`、`["org_structure"]`），前端唯一消费点是 `PlanEditorPage.tsx:471` 的**类型透传**——没有任何逻辑据此判断章节是否过期。

**后果**：用户改完企业信息/风险/资源后，已生成的章节正文仍是旧数据，系统不会提示"本章节依赖的数据已变更，建议重新生成"。这正是"改一处要手动动多处"的根源，且是全项目**成本最低的一致性改进点**（数据已经在库里，缺的只是消费方）。

### D-4（P3，潜在）平面图镜像单向同步

- 楼层 → 企业字段：`risk_management.py:136-138 / 163 / 187 / 208 / 286` 共 5 处同步（切换默认楼层、传图、清空、四色图提交）。
- 企业字段 → 楼层：`routers/enterprises.py:167` 的 `update_enterprise` 直接 `setattr(e, "floor_plan_url", v)`，**不碰默认楼层**。

**实测现状**：12 家既有平面图的企业，企业字段与默认楼层字段**全部一致**（尚未踩中）。
**风险**：用户在「企业档案」里换图后，四色图工作台/风险评估报告仍用旧图（它们读楼层），预案疏散图则优先楼层、回退企业字段 → 同一张图两处不一致。

## 三、已经做对的部分（"只填一次"真实成立的地方）

1. **企业基本信息**：单表 148 列中的企业部分，预案表零冗余（只有 `enterprise_id`）；一次填写，章节生成、风险评估报告、资源调查报告、危化品/风险/周边三类 AI 引导全部自动读取。
2. **人员只录一次**：`emergency_org_assignments.member_id` 外键指向 `enterprise_members`，应急组织**只引用不复制**人名/电话（模型注释明确"完全分离：应急角色只引用成员 id"）。
3. **应急资源**：表单、AI 生成、Excel 导入、批量四个通道全部落 `emergency_resources` 同一张表，内/外部用 `is_external` 区分，不是两张表。
4. **周边环境**：表单（`SurroundingInfoForm`）与 AI 生成（`SurroundingInfoPanel` + 高德检索）写同一个 `surrounding_info` 字段 —— 多入口单存储的正确做法。
5. **重大危险源 ↔ 既有模块**：单元品种可**从台账选择**（`GET /major-hazard/ledger/chemicals`）、设计最大量给**建议初值 + 口径提示且不自动落库**（`suggest-design-max`）、单元可关联风险点，且所有关联做**同企业校验**（`major_hazard_linkage.py` 注释：跨企业关联是安全事故级 bug）。这是全项目互联互通做得最扎实的一块。
6. **一次录入的加速器**：资料包导入 → AI 抽取候选 → 人工确认，覆盖 5 个模块（企业信息/应急组织/风险与危化品/应急资源/周边环境，`onboarding_service.MODULE_SCHEMA_HINTS`）；另有各域的 AI 问答生成与批量导入模板。
7. **风险旧数据的迁移向导**：不要求重新录入（见 D-1 的缓解措施）。
